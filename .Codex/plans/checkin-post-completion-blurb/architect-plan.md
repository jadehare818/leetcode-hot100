# Architect Plan — checkin-post-completion-blurb

## 总体思路
把“全部完成”拆成持续状态与首次完成日期两个概念：完成状态仍由非 `todo` 数量决定，首次完成日期则从当前有效题目的最早 `solve/archive` 历史推导。文案选择抽成可单测的纯逻辑，优先级调整为：起点 → 首次完成当天庆祝 → streak 里程碑 → 完成后的复习主题池 → 进行中的通用池 → 无活动兜底。

## 方案取舍
- 方案 A：用 `done_count == total and solved_ids` 判断完成当天。改动最小，但已完成题后续重标状态也会新增 `solve`，存在重复庆祝；不采用。
- 方案 B：从当前有效题目的首个 `solve/archive` 推导完成日。无需迁移数据，当前数据可准确还原 2026-08-07，且能排除后续重标；采用。
- 方案 C：新增全局 `first_all_completed_date` 持久化字段。可以表达“一生只庆祝一次”，但需要数据迁移并处理增删题、重置与元数据存储，超出本次需求；不采用。

## 复习主题文案
文案沿用现有短句、克制、轻松的口吻，避免在当天未复习时虚构“今天已复习”：

- 首刷收官，复习继续
- 题刷完了，手感还要续上
- 常回来看看，思路才不会生锈
- 把会做一次，练成随时会做
- 复习不赶路，贵在常回来
- 记住，比刷过更重要
- 刷完是进度，记住才算数
- 守住复习节奏，守住手感

## 测试计划
- 单元测试：运行 `./.venv/bin/python -m unittest tests/test_checkin_blurb.py -v`，覆盖空题集 / 未开始、部分完成、首次全部完成日、完成次日、完成后 streak 3/5/7/35、同题后续重标、孤儿进度、缺失与非法历史日期。
- 集成验证：使用 Flask `app.test_client()` 请求 `/api/checkin`，确认当前数据在 2026-08-09 不再返回庆祝语，而返回复习主题文案或合法 streak 里程碑；确认响应 key 集合不变。
- 手动验证：打开 Share → 打卡卡片，确认推荐语展示正常；保存 PNG 的内容与页面一致。前端不改，不需要额外交互回归。
- Edge cases：当前有效题目包含自定义题；软删题留有 progress；手动 archive；重标非 todo 状态；历史为空 / 日期非法；业务日边界不是自然日 00:00。

## 风险 / 偏离常规模式 / 注意事项
- 历史推导表达的是“当前有效题集在当前这轮中的首次完成”，不是跨题目增删与 reset 的永久全局里程碑；这是本次为避免新增 schema 的明确取舍。
- 每次打开打卡 API 会扫描当前题目的短历史。当前约百题规模开销很小；若题目和历史数量未来显著增长，再考虑持久化或缓存。
- 仓库此前没有测试框架；新增测试只依赖标准库和项目现有 Flask 环境，不改变运行时依赖。
